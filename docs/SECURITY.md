# Local security model

Aurora is an offline, single-user application, not a multi-user security boundary. Its controls reduce accidental exposure and prevent untrusted mutable installation state from being mistaken for verified release content. They do not make a compromised operating system, administrator account, or writable source checkout trustworthy.

## Release and build trust

The release maintainer verifies the outer ZIP SHA-256 from a separately trusted release record. A checksum next to a ZIP provides corruption detection only; it cannot prove origin when both can be replaced. Controlled distribution requires an organization-owned detached signature/trust anchor and an out-of-band public-key fingerprint. `prepare_release --signing-key ...` can optionally sign the final streaming SHA-256 with a user-supplied Ed25519 key and emits detached signature/public-key files, but Aurora generates no organizational key and makes no approval or certification claim. Inside the ZIP, `checksums.txt` covers immutable source, frontend, configuration, offline package cache, portable runtime archives, llama archives, and the pinned default model. Offline `build` verifies the manifest in both directions before changing installed state: every listed file must match, and every immutable file present must be listed. Duplicate/unsafe paths, links, hard-linked immutable files, missing required entries, and unexpected immutable files are rejected.

`.runtime`, `node_modules`, `data`, `.cache`, `exports`, and `config/app.local.json` are mutable by design and are not release-manifest inputs. Build therefore never executes an existing `.runtime`: after checksum verification it rejects linked/reparse mutable directories and unexpected stale runtime staging paths, stops owned processes, removes the old installed runtime, extracts a fresh candidate from the verified Node/llama archives, and runs tooling/self-tests only from that candidate. Build ignores `app.local.json` and uses the verified defaults, including the manifest-listed default model. The candidate is renamed atomically to `.runtime` only after all tests succeed. A failed build leaves no partially trusted canonical runtime, so `start` fails closed until build succeeds.

`npm ci --offline --ignore-scripts` reconstructs production `node_modules` from the checksum-protected package lock, vendored package, and content-addressed offline cache. Each prepared package contains `docs/release/aurora-intel.cdx.json`, a CycloneDX inventory of the full npm lock plus pinned Node/llama/model artifacts and hashes. The inventory and license gate support review but do not prove that no vulnerability exists now or will be disclosed later. `npm audit` requires current advisory data and belongs only in the connected release-review process, with dated results retained separately.

Connected development is a separate workflow. An explicit `npm run dev:ai` may download only the current-platform llama archive and model entries pinned by HTTPS URL and SHA-256 in `config/versions.lock`. Downloads are resumable, stored outside Git, and never extracted or executed until their complete digest matches. Normal development, release start, and offline target commands never invoke this downloader.

Additional user-selected GGUF files are intentionally outside the original release manifest. By default `start` refuses any selected model that is not both checksum-manifested and the destination of a `kind=model` lock entry. The exceptional `--allow-unverified-model` flag is required on each launch and prints a loud warning. Treat any such GGUF as separately supplied native-parser input: verify provenance and run llama.cpp within the organization's approved OS sandbox/VM or other containment boundary. Aurora configures loopback, process environment, paths, and retry limits but does not itself provide a cross-platform OS sandbox. An exact rebuild rejects the extra immutable file, so move it aside first or add its immutable URL/SHA to `versions.lock` and prepare a new controlled release.

The 4,372,812,000-byte default model and the full ZIP exceed FAT32's file-size limit. USB media and extraction tooling must support large files/ZIP64; exFAT is the ordinary cross-platform choice only when permitted by organizational policy.

## Local process and listener boundaries

The application and llama listeners bind to literal `127.0.0.1`; no setting can widen the address. The supervisor creates a fresh random 256-bit hexadecimal llama key in memory for each run. It supplies the key to llama-server as `LLAMA_API_KEY` and to the app child as `AURORA_LLM_API_KEY`. The value is not placed in command-line arguments, PID/state files, or logs. llama's public health route remains suitable for readiness checks, while model/inference requests require `Authorization: Bearer <key>`.

The supervisor independently generates a 256-bit application token and passes it only to the app child as `AURORA_APP_TOKEN`. With the exception of public `/api/health`, the API requires either its session cookie or a bearer token. `start` never prints or passes the token in a browser-launch command: it reads a private, regular, single-link `data/logs/session.token`, writes an exclusive transient local HTML bootstrap, opens only that file path, and removes it after a short cold-browser allowance. The browser exchanges `?session=...` for an HttpOnly, SameSite=Strict, Path=/ cookie and the server returns a 303 to clean `/`. State and console URLs remain clean. The supervisor forwards only an explicit platform environment allowlist to children, plus each child's required Aurora secret; inherited `NODE_OPTIONS`, loader variables, proxy variables, and unrelated secrets are not forwarded.

The build-time grammar test uses a separate ephemeral key in the same manner. This key limits unintended use by another local process during the run; it is not a credential for any remote service and is discarded when the process exits.

PID files and `data/logs/state.json` are mutable hints, not authority. `start` only treats a PID as an existing Aurora instance when the process is alive and its command line contains this release root and `scripts/supervisor.mjs`. It only accepts a state URL matching canonical `http://127.0.0.1:<1-65535>` with no path, query, credentials, or alternate host. Invalid/stale values are ignored. `stop` likewise signals only processes whose command line belongs to this release root. Mutable `data`, `logs`, and `exports` directory components must be real directories rather than symlinks/junctions. Log creation uses exclusive/no-follow opens plus regular-file/link-count checks (or safely recreates the filename before Windows redirection), so preseeded symlinks and hard links are never used as write targets. Supervisor-owned logs rotate at 10 MiB with five files retained; five llama exits inside two minutes stop automatic retries and record a circuit-open status until stop/start.

## Frontend offline guard

Both the release and test guards scan built HTML, JavaScript, CSS, JSON, source maps, SVG, text, and XML. Before matching they repeatedly reveal common hiding forms: JavaScript Unicode/hex/octal escapes, escaped slashes, percent encoding, numeric/named HTML entities, simple string concatenation, static `atob(...)`, and static `String.fromCharCode(...)`. They reject external `http`, `https`, `ws`, `wss`, and protocol-relative domain references. Only explicit `127.0.0.1`/`localhost` URLs are network allowlisted.

Five exact W3 DOM namespace identifiers are a narrow non-network exception because browsers and SVG libraries use them as identifiers passed to namespace-aware DOM APIs, not as fetch targets: SVG, XHTML, XLink, XML, and MathML. Any longer path/query under those hosts still fails. The scanner is a defense-in-depth static gate; runtime CSP and literal loopback binding remain mandatory.

## Data and operational limits

- The browser token blocks unauthenticated loopback requests, but it does not protect against other software running as the same OS user. Use a dedicated, controlled workstation profile and normal endpoint protections.
- The transient bootstrap reduces accidental cross-process access but is not a boundary against the same OS user or an administrator. On Windows—especially removable exFAT media—POSIX-style mode `0600` is not equivalent to a centrally managed NTFS ACL; copy the release to the controlled local user profile as instructed.
- Full reports, exports, backups, and logs stay under the release folder. Filesystem permissions, disk encryption, removable-media controls, and organizational handling rules remain external responsibilities.
- AI output is untrusted draft data. JSON schema enforcement, vocabulary checks, cited IDs, coordinate/time post-processing, and human review are required before save.
- Aurora is not a safety, emergency, navigation, targeting, or legal-boundary system.

For a suspected altered package, do not bypass a checksum or guard. Obtain a fresh release and compare the outer ZIP digest through the approved release channel.
